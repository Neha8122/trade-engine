Ring Buffer LLD

The pipe between threads. One thread writes, one thread reads, and they never take a lock. This is how the sequencer hands orders to the matching engine, and how the engine hands results to the publisher.

6 · API, full and empty, and code layout

public final class SpscRingBuffer<E> {

  // capacity: power of 2
  // factory:  creates every slot once, up front
  SpscRingBuffer(int capacity, Supplier<E> factory)

  // Producer thread only
  E    claim()      // slot to fill, or null if full
  void publish()    // makes the claimed slot visible

  // Consumer thread only
  int  drain(EventHandler<E> h, int max)
                    // handles up to max, returns count
}

interface EventHandler<E> {
  void onEvent(E event, long sequence);
}

When it's full or empty

Fullclaim() returns null. The producer decides: the gateway rejects the order (backpressure), it never blocks the engine.
Emptydrain() returns 0. The consumer loop chooses a wait strategy: busy-spin with Thread.onSpinWait() for lowest latency (burns a core), or yield / park to save CPU.

7 · How we'll prove it's correct

TestWhat it checks
Single-thread unit testsempty → drain 0; fill to capacity → next claim null; drain frees space; wrap past slot 15 many times; max limits a batch
Two-thread stress testproducer sends sequence numbers 0…10M with a checksum in each message; consumer checks every message arrives once, in order, uncorrupted. A memory-ordering bug shows up here as a torn or stale message
Tiny-buffer stresscapacity 2, so the full/empty edges are hit millions of times
Benchmarkmessages per second and ns per message, ours vs ArrayBlockingQueue, same two threads

Interview line: "A lock-free bug doesn't fail every time, so the stress test runs millions of handoffs with the buffer constantly full or empty, which is where ordering mistakes show up."
